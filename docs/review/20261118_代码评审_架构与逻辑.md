## 1. 系统与架构（供复核者快速建模）

### 1.1 边界与数据流

```
        BMI323 (3.2 kHz, ±16 g)                     CH592F 网关                  PC
  ┌───────────────────────────┐            ┌────────────────────────┐      ┌────────────────┐
  │ SPI0 7.5MHz, FIFO 35帧水位 │            │ RF AUTO 1M 2450MHz     │      │ 浏览器观测台    │
  │ PA4 INT1 → FIFO_EVT        │  2.4GHz    │ rx_queue 8 槽          │ USB  │ web/index.html │
  │ sampler → sample_clock     │ ─────────> │ ACK 双缓冲 + 确认表8   │ ───> │ (Web Serial)   │
  │   (编号/分段/锚点/GAP)     │  DATA/     │ host_link 261B 帧      │ CDC  │ 去重/绘图/CSV   │
  │ packer → pkt_ring 22 槽    │  STATUS/   │ TIME_REQ/HELLO/        │      └────────────────┘
  │ rf_tx: RF_Tx 等 ACK        │  POLL      │ GW_STATUS/下行命令      │
  │ (等待循环全部在 RAM)        │ <───────── │ 反压：槽<2 不挂接       │
  └───────────────────────────┘   ACK      └────────────────────────┘
```

### 1.2 模块职责（节选，完整表见 `docs/01 §9`）

| 文件 | 职责 | 关键约束 |
|---|---|---|
| `firmware/common/proto.{h,c}` | 协议常量、偏移枚举、显式小端读写、RF 包合法性 | 不把 C 结构体当线格式 |
| `firmware/sensor/app/sample_clock.c` | 传感器时间连续性 → `sample_idx`/`segment`/锚点/缺样数 | 只用整数；无符号 16 位差 |
| `firmware/sensor/app/sampler.c` | FIFO 读空、轮次上限、停采探测、健康恢复 | 时间锚点必须在 burst 之后取 |
| `firmware/sensor/app/pkt_ring.c` | 22 槽、满则丢最老、`oldest_seq`、确认释放、超时回队 | 只有确认表命中才释放 |
| `firmware/sensor/app/rf_tx.c` | TX_EVT 状态机、ACK 解析、退避、同步配对 | 等待路径整链 `__HIGH_CODE` |

| `firmware/gateway/app/host_link.c` | 主机帧编码、帧优先级、USB 分片交付 | 整帧交付后才 `gw_queue_pop` |

### 1.3 四个关键机制（评审时重点看的就是这四处）

1. **硬件 ACK ≠ 送达**。AUTO 模式的 ACK 载荷在收包前固定，共享信道会误确认；所以网关把"最近成功入队的 8 条 `(node_id, seq_lo16)`"塞进**下一个** ACK，节点看到自己才释放。节点启动先完成 2 次 POLL，网关按 `boot_id` 变化清旧表。这套机制我核对过实现与测试，**是对的**。
2. **反压靠"不挂接"而不是"丢包"**。`gw_can_rearm()` 要求队列 ≤ 6，否则停止挂接，节点收不到 ACK 自行重传。因此 `queue_full` 计数长期为 0 是**正常**的，不能据此判断"没发生过反压"。
3. **RAM/Flash 分区**。26 KiB RAM 中，`Link.ld` 把 `.highcode` 放在 RAM 起始，再用 `ASSERT(_ebss <= _susrstack)` 保 2 KiB 栈；链接后再由 `tools/check_firmware.py` 校验 `RF_Tx/RF_Rx/.../GPIOA_IRQHandler/USB_IRQHandler` 的符号地址确实落在 RAM。这是本项目质量最高的部分。
4. **三级时间模型**：`sample_idx → 节点 RTC → 网关 µs → UTC`。f1 用锚点线性拟合，f2 用 `(sync_txdone, rx_us)` 配对，f3 用 TIME_REQ/RESP 做类 NTP。

### 1.4 架构评价（**主观判断，供参考，不是缺陷**）

**优点**

- 生产者/消费者边界清晰：ISR 只做「抓时间、拷贝、置标志、`tmos_set_event`」；所有 RF API 主循环调用。
- 首发与重传、`QUEUED/WAIT_CONF`、退避都收敛在 `rf_tx.c` 一个状态机里，没有散落到采样路径。
- 协议显式序列化 + 偏移枚举，跨 C/JS 三方解析可行。
- 失败语义诚实：文档明确写清"哪些故障 V1 无法逐样本归因"，代码里对应 `AMBIGUOUS`/`UNKNOWN_SAMPLE_LOSS`，没有把歧义包装成已验收。
- 宿主测试不是摆设：时间回绕、假 8192 缺口、boot 断电、误确认、USB SETUP 语义都有回归（见 §7）。

**弱点**

- 协议有 **4 份独立实现**（`proto.h`、`docs/02`、`docs/site/js/*`、`web/js/protocol.js`），只有各自的固定向量，没有跨实现一致性校验（F14）。
- 模块间靠 3 个 `extern` 全局结构（`sensor_config/sensor_stats/sensor_ring`）串联，边界靠约定而非接口（F14 同源）。
- 主机侧"唯一事实来源"缺失：原始主机帧日志没有落盘能力（F16）。
- 无版本控制（F15）。

## 3. 逐条发现

### F01 · `rearm_lat_max_us` 把背压时长算成重挂延迟（P1，确认）

**位置**：`firmware/gateway/app/radio.c`，`rearm()` 与 `gateway_radio_poll()`

**关键片段**

```c
static GW_RAM void rearm(uint32_t now)
{
    PFIC_DisableIRQ(BLEL_IRQn);
    RF_Shut();
    listening = 0;
    if (!gw_can_rearm(&gateway)) {
        PFIC_EnableIRQ(BLEL_IRQn);
        return;                       /* ← 队列满：直接返回，idle_at 保持不变 */
    }
    ...
    if (result == 0) {
        listening = 1;
        if (idle_at != 0) {
            uint32_t latency = gateway_now_us() - idle_at;
            if (latency > gateway.rearm_lat_max_us) gateway.rearm_lat_max_us = latency;
            idle_at = 0;
        }
    }
```

`idle_at` 只在 `RX_MODE_TX_FINISH / RX_MODE_TX_FAIL` 回调里被置为当前时刻。

**机制**：队列满 → 不挂接 → 长时间不监听（这是设计好的反压）。但 `idle_at` 停留在"上一次成功收包结束"的时刻。等主机恢复读取、队列排空、第一次真正重挂成功时，`now - idle_at` 覆盖了**整段不监听时间**，被当作"重挂延迟"写入 running max，永久污染。

**证据（实测）**：`build/gateway-live-20261118-02-diagnostics.json` 第 166、171 行：

```
"rearm_lat_max_us": 1579055445
```

1 579 055 445 µs ≈ **26.3 分钟**，而该次抓包只持续 **30 秒**。物理上不可能是重挂延迟。

补充佐证：同一时段 `queue_full` 为 0——这正是 §1.3 第 2 条说的"反压不丢包、只停挂接"，与本缺陷自洽；也说明不能用 `queue_full==0` 反证"没有停过挂接"。

**复核判据**

- 成立：确认 `!gw_can_rearm()` 分支在 `idle_at` 清零之前 return，且 `gateway_radio_poll()` 里"1 s 无回调"分支因 `listening==0` 不会触发。
- 不成立：若能找到其他在"停止挂接"期间把 `idle_at` 清零或重置的路径。

**影响**：`docs/11` 接板验收第 3 步"测重新挂接延迟"以及 `docs/02 §6` "用 GPIO + 逻辑分析仪实测网关重新挂接延迟"的软件对应指标失效。此值还会出现在每个 `GW_STATUS` 里被上位机记录。

**建议**：`!gw_can_rearm()` 分支中 `idle_at = 0;`；或引入 `was_listening` 标志，只在"上一状态是 listening 且间隔 < 1 ms"时统计。

### F02 · 栈无 guard、无水位；RAM 余量 40~48 B（P1，事实确认 / 影响未测）

**位置**：`firmware/Link.ld`、`tools/check_firmware.py`、`build/firmware-memory.json`

**关键片段**

```ld
__stack_size = 2048;
...
.stack ORIGIN(RAM) + LENGTH(RAM) - __stack_size :
{ ... PROVIDE(_susrstack = .); . = . + __stack_size; PROVIDE(_eusrstack = .); } >RAM
ASSERT(_ebss <= _susrstack, "RAM exhausted: less than 2048 bytes reserved stack")
```

`build/firmware-memory.json`：

| 构建 | 静态 RAM + RAM 代码 | 预留栈 | 剩余 |
|---|---:|---:|---:|
| sensor | 24 120 | 2048 | 456 |
| sensor-debug | 24 140 | 2048 | 436 |
| gateway | 24 528 | 2048 | **48** |
| gateway-debug | 24 536 | 2048 | **40** |

**事实**：2 KiB 是**预留值**，不是实测最坏深度；`.stack` 下方紧贴 `.bss`，没有 guard word，也没有 high-water mark 上报。栈向下生长，溢出会静默改写 `.bss`（`gateway`、`sensor_ring` 等），现象会是"偶发协议错乱"，极难定位。

**最受影响的路径**：`host_link.c: choose_frame()` 有 `uint8_t out[GW_RF_MAX + 7u]`（253 B）局部数组，向下调用 `host_frame_encode()` → `crc16_ccitt()`，再叠加 USB ISR / BLEL ISR 嵌套。这条路径每次发 RF 帧都会走。

**复核判据**

- 成立：确认 `Link.ld` 无 guard、代码中无栈涂色/水位统计、`choose_frame()` 局部数组大小如述。
- 部分成立：若认为编译器栈用量分析已足够，请给出依据（本评审不采信"经验够用"）。
- 不成立：若能指出已有栈深度测量手段。

**影响**：这是"能不能上 24 h 长跑"的前置条件，不是可选项。一旦溢出，症状会表现为数据错乱而非崩溃，排查成本极高。

**建议**：启动时把 `_susrstack.._eusrstack` 填 0xA5，在 `GW_STATUS` 的保留字段（offset 24，当前固定写 0）里上报剩余最小深度；或至少在 `check_firmware.py` 里把 `spare` 门限从 `0` 提到 `16`，并加一条"栈使用 > 1.5 KiB 即失败"的链接期断言（做不到就退化为运行期上报）。

### F03 · 节点看门狗在 RF 初始化之后才使能（P1，确认）

**位置**：`firmware/sensor/app/main.c`

**关键片段**

```c
    board_init(); config_load();
    CH59x_BLEInit(); HAL_Init(); RF_RoleInit();
    sensor_task = TMOS_ProcessEventRegister(sensor_process);
    sensor_stats.streaming = 1;
    radio_init(); sampler_init(); board_fifo_interrupt_enable();
    WWDG_SetCounter(0); WWDG_ResetCfg(ENABLE);      /* ← 看门狗在这里才开 */
```

而 `radio_init()` 失败时（`firmware/sensor/app/rf_tx.c`）：

```c
    if (RF_Config(&config)) {
#if SENSOR_DEBUG
        PRINT("RF_Config error\n");
#endif
        while (1) { __nop(); }
    }
```

### F05 · 回绕补偿只按整圈 8192 样本补（P3 现状 / P2 模式 B 前必改，确认，已实测）

**位置**：`firmware/sensor/app/sample_clock.c`，`sample_clock_next()`

**关键片段**

```c
    uint32_t period = 1u << (16u - odr);
    uint32_t dt = (uint16_t)(sensor - c->last_sensor);
    uint32_t elapsed = sample_rtc_elapsed(rtc, c->last_rtc);
    if (c->valid && elapsed > 2u * 32768u && elapsed <= 60u * 32768u) {
        uint32_t estimate = (uint32_t)((uint64_t)elapsed * 25u / 32u);
        if (estimate > dt + 32768u)
            dt += ((estimate - dt + 32768u) / 65536u) * 65536u;   /* ← 只能补整圈 */
    }
```

**机制**：该分支假定"传感器一直在采样，只是我们没去读，所以传感器时间可能回绕了 k 圈"，于是用 RTC 间隔估计 k，把 `dt` 凑成 65536 的整数倍。65536 tick = 2.56 s = 8192 样本。

**这个假定只在"采样未中断"时成立**：此时 `estimate - dt` 恰好是 65536 的整数倍，补偿**精确**；一旦传感器真的停采（时间基准继续走但没有样本产生），`estimate - dt` 不是整圈，代码会把差额四舍五入成整圈，于是**凭空补出 8192 的整数倍样本**。

**实测 A：连续采样（假定成立的场景，补偿精确，见 §7 命令 C2）**

| 场景 | 真实丢失 | 固件 `missing` | 判断 |
|---|---:|---:|---|
| 连续丢 6400 样本（2.00 s） | 6400 | 6400 | 正确 |
| 连续丢 8192 样本（2.56 s，正好整圈） | 8192 | 8192 | 正确 |
| 连续丢 9600 样本（3.00 s） | 9600 | 9600 | 正确 |
| 连续丢 16384 样本（5.12 s，两整圈） | 16384 | 16384 | 正确 |

**实测 B：传感器停采（假定不成立的场景，见 §7 命令 C）**：输入取"恢复后相邻样本 `dt=8`"，RTC 间隔如下。

| 场景（停采后恢复） | 真实丢失 | 固件 `missing` | flags | 判断 |
|---|---:|---:|---|---|
| 1.90 s | 0 | 0 | 0x00 | 静默当作连续 |
| 2.00 s | 0 | 0 | 0x00 | 静默当作连续（边界 `>` 不成立） |
| 2.10 s | 0 | **8192** | 0x01 GAP | **虚报 8192** |
| 2.50 s | 0 | **8192** | 0x01 GAP | **虚报 8192** |
| 5.00 s | 0 | **16384** | 0x01 GAP | **虚报 16384** |
| 61 s | — | 0（新段） | 0x08 NEW_SEGMENT | 符合文档 |

**可达性分析（这条决定严重度，请复核者重点看）**

- 在模式 A 下该分支**几乎不可达**：若传感器真的持续采样 2 s，FIFO（80 ms 容量）必然满，会先走 `sampler.c` 的 `fifo_unknown` 早退路径；若传感器停采，1 s 一次的 `sampler_health()` 会先 `sample_clock_reset()`（`valid=0`）使该分支被跳过。
- 于是"该分支唯一可达的场景" ≈ "传感器停采但未被 health 发现"，而这恰恰是它会**凭空补 8192 整数倍样本**的场景。前提与实现是反的。
- **但在模式 B/休眠下这个前提会成立**：`docs/05` 的休眠调度会让相邻处理间隔达到秒级且 FIFO 不满，届时该分支会稳定触发并虚报。**这是模式 B 开工前必须修的前置项。**

**复核判据**

- 成立：用 §7 命令 C 复跑，得到上表最后三列的数值。
- 部分成立：若认为"2.1 s 停采时虚报 8192"是刻意设计（把不确定量按整圈上报），请在 `docs/02 §7` 找到相应说明——目前文档只说"补上 65536 的整数倍"，未说明会**制造**样本。
- 不成立：若能给出模式 A 下让该分支收到"连续真实丢样"的路径。

**建议**：核心问题不是"补多少"，而是"该不该补"。本项目自己的原则是**不虚构未知丢样数**（`docs/10 §3.5`、`docs/11` 都写了）。据此两种改法：

1. **缩小适用面**：只有当能确认"采样未中断"时才做整圈补偿（例如 `flags & SAMPLE_FIFO_FULL`，或 FIFO 填充持续增长）；其余情况按 `sample_clock_reset(SAMPLE_NEW_SEGMENT)` 开新段，交给上位机记"未知损失边界"，与 `fifo_unknown` 路径的处理保持一致。
2. **若仍要在停采场景给数**：必须写成"至少 / 约"，并在 `docs/02 §7` 明确该量是估计值，否则上位机会把它当精确缺口写进 `gaps` 表，与验收要求"每个缺口都有准确样本区间和原因"冲突。

### F10 · `sampler_health` 复位与 `fifo_unknown` 复位标志不一致（P3，确认）

### F11 · 锚点 `ticks * 32 / 25` 截断（P3，确认，数学）

**位置**：`firmware/sensor/app/sample_clock.c:13`

```c
    uint32_t age = (uint32_t)(uint16_t)(sensor_now - sensor) * 32u / 25u;
    return read_rtc >= age ? read_rtc - age : RTC_MODULUS - age + read_rtc;
```

**机制**：整数截断使 `age` 偏小 0~1 个 RTC tick，锚点因此**系统性偏晚**（不是偏早）最多 1 tick（30.5 µs）。§4 实测显示包间锚点差的标准差只有 0.80 tick，说明这一项与 RTC 量化一起构成了本地噪声底。

**复核判据**：成立 = 数学上确认截断方向。数值影响应 ≤1 tick，复核者若实测到 ±2 tick，说明还有 RTC 读量化叠加（本评审也是这样解释的）。

**建议**：`(ticks * 32u + 12u) / 25u`（四舍五入）。收益有限（≤15 µs），但零成本。

## 4. 专项：`f1 = 615.207 µs` 的归因（不是缺陷，请只复核数值与推理）

### 4.1 问题

`docs/11` 记录实板 30 s 采集的三级残差为 f1 = 615.207 µs、f2 = 8.494 µs、f3 = 17.281 µs，并写"仍需定位采样锚点及拟合误差"。f1 高于 `docs/03 §2.5`（<50 µs）和 `docs/04 §4`（<100 µs）。

### 4.2 方法

我写了一个独立脚本 `docs/review/f1_anchor_check.py`（无第三方依赖），它自己拆原始日志记录 → 验主机帧 CRC → 解 `RF_RX` → 解 DATA 头 → 取 `(anchor_idx, anchor_us)` → 按 `RTC_MAX_COUNT = 0xA8C00000` 展开 → 与上位机等价地做直线拟合。复跑方式见 §7 命令 B。

数据：`data/gateway-live-20261118-02/raw/20261118/01_gw1.bin`，boot 6，2 765 个唯一 DATA 包（全部 `n=35`，`segment` 只有 29，样本编号零不连续，30 个 seq 缺口）。

### 4.3 结果

```
整段单窗口拟合：斜率 10.231706 RTC tick/样本 → 3202.59 Hz
                残差 RMS 20.52 tick = 626.2 µs      ← 与文档 615.207 µs 吻合（我的实现未做 3σ 剔除）
相邻包锚点差：   均值 358.09 tick，标准差 0.80 tick，只取 5 个整数值

残差 RMS 随拟合窗口：
    35 包 ≈  0.38 s :   0.57 tick =  17.5 µs
    70 包 ≈  0.77 s :   0.77 tick =  23.4 µs
   175 包 ≈  1.91 s :   1.58 tick =  48.3 µs
   350 包 ≈  3.83 s :   3.35 tick = 102.1 µs
   700 包 ≈  7.66 s :   6.50 tick = 198.5 µs
  1400 包 ≈ 15.31 s :   8.04 tick = 245.2 µs
  2765 包 ≈ 30.24 s :  20.52 tick = 626.2 µs
```

### 4.4 推理与结论

1. **锚点公式不是主因**。相邻包锚点差的标准差只有 0.80 tick（24 µs），且只取 356/357/358/359/360 五个整数值——这正是"RTC 整数 tick + `32/25` 截断"的量化特征。锚点公式即使按 F11 修好，也只能消掉 ≤15 µs。
2. **残差随窗口近似线性增长**（0.38 s→17.5 µs，1.91 s→48 µs，7.66 s→198 µs，30 s→626 µs）。白噪声的随机游走会按 √n 增长，线性增长意味着**采样时钟(RTC 与 BMI323 ODR 之比)存在持续偏移式的漂移**，量级 ≈ 626 µs / 29 s ≈ 21 ppm。
3. 因此 **615 µs 是"用一个 29 s 长的线性模型去套 ±20 ppm 漂移"的必然结果，不是单个样本的时间误差**。样本级精度受锚点量化限制在 ~±1 tick（30 µs）量级。
4. **不确定的部分**：我的数据无法区分漂移来自 BMI323 的内部时钟还是外部 32.768 kHz 晶振（f2 显示节点 RTC 相对网关 60 MHz 偏 +112 ppm，f3 显示网关相对 PC 偏 −5.9 ppm；把 f1 的等效 3202.59 Hz 按 RTC 偏差折算后约 3202.2 Hz，与 STATUS 统计的 3201.38 Hz 相差约 265 ppm，而分块速率估计本身的波动带约 ±300 ppm，三者处于同一量级）。**这一点请复核者不要采信任何单一归因**。

### 4.5 对验收指标的建议

- 若坚持 `<50 µs`：必须把 f1 的拟合窗口缩到 ≤2 s（本数据 1.91 s 窗口 = 48.3 µs，**刚好达标**），或改成分段/样条模型；同时把 `docs/03 §2.5` 的"30 s 滑动窗口"改掉。
- 若坚持 30 s 单窗口：则应把指标定义为 **残差 + 速率漂移**，或改成"相邻样本时间差误差"这类局部量。
- 无论哪种，都需要先把 F16（原始日志落盘）补上，否则该指标仍只能靠一次性脚本复核。
