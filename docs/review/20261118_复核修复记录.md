当前修正版：节点 v1.3，网关 v1.4。首批节点 v1.2 / 网关 v1.3 存在下述启动权限错误，应使用重新生成的 HEX；修正版尚待重新刷写验证。

### 刷写后无 CDC 的启动修复

用户反馈网关 v1.3 下载、校验成功（`Verify OK`）并复位后没有 CDC 串口。
独立核对链接产物发现：厂家 `handle_reset` 写入 `mstatus=0x88` 后执行 `mret`，此时 `MPP=0`，
应用入口已在用户态。新增 `__wrap_main` 的第一条指令却是 `csrrci t3,mstatus,8`，
访问机器态 CSR `0x300`，会在进入 C `main()` 前触发权限异常，USB 初始化无法执行。
节点 v1.2 使用同一公共入口，也受影响。

- `common/stack_start.S` 改为厂家 SDK `__risc_v_disable_irq` / `__risc_v_enable_irq` 使用的用户态 CSR `0x800`，保存、清除并恢复 `0x88` 中断使能位；涂色范围和 2 KiB 栈不变。
- `tools/check_firmware.py` 解码实际链接后包装入口的 CSR 指令，拒绝要求更高权限的访问；旧网关、节点日志版 ELF 均被该检查以 `privileged CSR 0x300` 拒绝。
- 修正后的四套固件均已重建，通过用户态 CSR、RAM 预算和 RF/中断地址检查；12 个宿主 C 测试程序通过 ASan/UBSan。反汇编确认入口只访问 CSR `0x800`，涂色后跳入真实 `main()`。
- 网关版本更新到 v1.4，节点更新到 v1.3，便于与启动失败的构建区分。尚未将修正版刷到实板，CDC 枚举与节点启动仍需现场确认。

### 查看栈水位

MounRiver 调试器中观察 `app_stack`：

- `reserved_bytes`：链接器实际预留栈大小，当前 2048 B。
- `free_min_bytes`：启动以来观测到的最小未触及区，按 4 B 粒度统计；不是静态 RAM 的剩余空间。
- `guard_fault`：栈底 16 B 曾被改写时锁存为 1；这是软件告警，不会阻止越界写入。

节点每次 STATUS 前更新，日志版同时输出 `stack` / `guard`；网关在启动及每 120 s 的射频停止校准窗口更新。
记录 24 h 长跑后的最小剩余量与哨兵状态，实板最大栈深度仍待测。
网关控制回复缓存按实际最长 12 B 分配，保持四个回复槽、八个 RF 槽及原有帧布局。

## 原报告需修正的判断

- F01 是指标口径污染；历史最大值可能来自抓包前，不能用 30 s 抓包时长否定累计值。
- F02 的 40～48 B 是预留 2 KiB 栈以外的余量，尚不能证明实际栈溢出。
- F05 的合成输入可复现，但模式 B 每 50 ms 读取 FIFO，并非秒级处理；保留有条件风险，不修改时间编号算法。
- F10 两种恢复路径原因不同，不统一强加 FIFO_FULL 标志。
- F11 数学方向为锚点偏晚，原汇总表“偏早”有误；本批不修改锚点算法。
- F12 停止采样后仍可重传旧 DATA，约 5.36 s 的模拟失败重传已达到 attempt=255，不能依赖缓存淘汰排除。
- F13 撤回：`gw_queue_command()` 已拒绝命令 ID 为 0。
- F15 无 Git 仓库属实，外部备份情况未知；本轮不执行 Git 初始化或提交。

## f1 数值复核

既有 boot 6 原始日志的整段 RMS 为 626.179 µs；原脚本输出可以复现。
175 包约 1.91 s 的分块残差合并后为 48.3 µs，但完整分块最大为 92.42 µs；
滑动窗口最大为 114.07 µs，2591 个窗口中 824 个超过 50 µs。
因此不能宣称“缩到 2 s 即达标”，也不能以 RMS/时长推得 ±20 ppm 时钟漂移。
原始时间验收指标与网页既有时间估算语义保持不变。
