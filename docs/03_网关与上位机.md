# 03 网关与上位机

本文保留完整系统设计；当前阶段一为单节点、单网关、2450 MHz / 1M，实施范围以 10 为准。
第 1 节为网关主机接口，第 2 节保留上位机设计要求。原 Python PC 工具已移除；固件入口和历史实测记录见 11。

## 1. 网关固件（CH592F，USB CDC 接 PC）

完整部署设计中，网关沿线固定安装并记录线体坐标（米）：模式 B 用 E1/E2/E3、1M PHY，模式 A 参考区用 S1/S2、2M PHY。当前构建从单频点 1M 起步，尚未启用漫游。

模板：RF 部分按 `EVT/EXAM/BLE/RF_PHY` 例程的 RX 方向改写；队列参考 `EVT/EXAM/BLE/BLE_USB/APP/RingMem.c`。
与 PC 的连接做成 `net_link` 接口：
- 当前实现：USB CDC（`EVT/EXAM/USB/Device/COM`，BLE 库与 USB 共存参考 `BLE/BLE_USB`）。远距离部署的串口/TCP 转发方案见 10 §3.4。
- 以后可选：若网关 PCB 有以太网芯片，改为 TCP Client 直连服务器。串口转以太网芯片（如 CH9120）走 UART；SPI 以太网芯片（如 W5500、CH395）挂 SPI0。
  TCP 时，网关主动连服务器（IP/端口存 DataFlash），断线按 1 s、2 s、4 s…最长 30 s 重连，关闭 Nagle。

接收流程：

```
REARM_EVT:
  rx_queue 剩余槽 < 2 → 不挂接收，1 tick 后重试（反压：节点收不到 ACK 会自己缓存重发）
  在非活动的 ACK 缓冲里写入最新 ACK（确认表 + 待下发命令），切换活动缓冲
  RF_Shut(); RF_Rx(ack_buf, ack_len, 0xFF, 0xFF)
回调 RX_MODE_RX_DATA（中断）:
  抓 SysTick 微秒；crc==0 且负载合法 → 把时间、RSSI、长度、负载拷进 rx_queue（单生产者单消费者环形队列），
  成功入队的 DATA/STATUS 才把 (node_id, seq_lo16) 记入确认表（最近 8 条）；POLL 不入确认表
  crc!=0 → 计数 crc_err / type_err
回调 RX_MODE_TX_FINISH / RX_MODE_TX_FAIL → tmos_set_event(REARM_EVT)
NET_EVT（周期 1 tick）: rx_queue → 封成主机帧 → net_link 发送；主机链路未就绪（CDC 未打开或 TCP 未连接）时保留在队列里
STATUS_EVT（1 s）: 上报网关计数器
```

- ACK 缓冲在挂接收期间不能改动，所以用双缓冲。
- 不做去重、不做排序，收到即转发，同一个包被多个网关收到由服务器合并。
- 确认表只记 crc 正确、负载格式合法、已成功放进 rx_queue 的包；主机链路断开且队列满时网关停止挂接收，节点会缓存，不会误确认。
  已知限制：网关突然掉电时，队列里已确认但未发出的包会丢失，服务器端表现为 RADIO 缺口。物理容量 8 包，正常反压门限最多积压 7 包。
- 保护：挂接收后 1 s 内没有任何回调就 `RF_Shut` + 重新挂接；开硬件看门狗。
- 初始设计估计 `rx_queue` 为 16 槽；当前构建按 26 KiB RAM 和 2 KiB 栈实测配置为 8 槽，保持厂家 6 KiB 协议栈堆。模式 A 约 25 kB/s，USB 全速 CDC 远大于此。

### 1.1 主机帧格式（CDC 或 TCP 字节流，帧相同）

`0xA5 0x5A | u8 type | u8 frame_seq | u16 len | payload[len] | u16 CRC16-CCITT(type..payload)`

CRC 采用 CRC-16/CCITT-FALSE：多项式 0x1021，初值 0xFFFF，不反转，无最终异或；校验范围从 type 到 payload 末尾，结果小端存放。`len` 为 payload 字节数（小端）。

#### CRC 的精确定义（网页解码器与后续固件/PC 实现共用）

| 参数 | 值 |
|---|---|
| width / poly | 16 / `0x1021`（省略最高项 x¹⁶） |
| init / xorout | `0xFFFF` / `0x0000` |
| refin / refout | false / false（字节不反转，逐位从高位处理） |
| check | ASCII `123456789` → `0x29B1`；空输入 → `0xFFFF` |
| 覆盖范围 | 从帧偏移 2 的 `type` 开始，包含 `frame_seq`、`len` 的两个小端字节及全部 payload；共 `4 + len` 字节 |
| 不参与计算 | 帧头 `A5 5A` 和末尾的 CRC 两字节 |
| 结果存放 | 低字节先发，高字节后发；CRC 偏移为 `6 + len`，整帧长度为 `8 + len` |

逐字节参考实现（输入为上述覆盖范围，不是完整帧）：

```python
def crc16_ccitt_false(data: bytes) -> int:
    crc = 0xFFFF
    for byte in data:
        crc ^= byte << 8
        for _ in range(8):
            crc = ((crc << 1) ^ (0x1021 if crc & 0x8000 else 0)) & 0xFFFF
    return crc
```

可直接粘贴到 `site/index.html` 解码器的整帧测试向量：

- GET_INFO：`A5 5A 83 00 00 00 24 C2`。CRC 输入 `83 00 00 00`，结果 `0xC224`，帧末为 `24 C2`。
- TIME_REQ（frame_seq=1、req_id=1）：`A5 5A 81 01 04 00 01 00 00 00 18 43`。CRC 输入 `81 01 04 00 01 00 00 00`，结果 `0x4318`。

这层 CRC 用于 CDC/TCP 主机帧，与 02 中由 RF 硬件处理的无线 CRC / `CRCInit` 是两层独立校验。

| type | 方向 | 负载 |
|---|---|---|
| 0x01 RF_RX | 网关→服务器 | u8 gw_id, u32 rx_us, i8 rssi, u8 rf_len, rf_payload[rf_len] |
| 0x02 TIME_RESP | 网关→服务器 | u32 req_id, u32 t_req_us（收到请求时刻）, u32 t_resp_us（发出响应前时刻） |
| 0x03 GW_STATUS | 网关→服务器 | rx_ok, crc_err, type_err, queue_full, net_drop, rearm_lat_max_us, tcp_reconnect（各 u32） |
| 0x04 CMD_RESP | 网关→服务器 | u8 req_type, u8 result |
| 0x05 HELLO | 网关→服务器 | 8 B：u8 gw_id、u8 fw_major、u8 fw_minor、u32 frequency_khz、u8 phy（1=1M，2=2M）；连上后第一帧 |
| 0x81 TIME_REQ | 服务器→网关 | u32 req_id |
| 0x82 QUEUE_DOWNLINK | 服务器→网关 | u8 node_id, u8 cmd_id, u8 cmd_code, u8 cmd_len（≤ 8）, payload[cmd_len]（与无线 ACK 命令区一致） |
| 0x83 GET_INFO | 服务器→网关 | — |
| 0x84 SET_GW_CFG | 服务器→网关 | gw_id、频点、access address、CRCInit、PHY、服务器地址，写入 DataFlash |

`frame_seq` 用于发现网关内部丢帧（计数）。CDC 和 TCP 本身都可靠，不另做重传。

阶段一 `SET_GW_CFG` 返回不支持，避免对尚未定义的配置字节布局写入 DataFlash。
网关 ID 和 RF 参数通过构建宏设置。`CMD_RESP.result`：0 已排队（不等于节点已执行），1 格式错误，
2 不支持，3 下行命令槽忙（v1.5 起同 `node_id` 新命令直接覆写旧待发槽并即时触发重挂刷新 ACK，仅 8 个槽被不同节点占满时返回 3；详见 `docs/13`）。

每次网关启动或 CDC 会话重建，固件先发送完整 HELLO，再发送 RF_RX；USB 中断时未完整交付的 RF 包在新 HELLO 后完整重发。
GET_INFO 也返回 HELLO，因此不能仅凭收到 HELLO 判断网关重启。

## 2. 上位机设计要求（推荐 Linux 工控机 + chrony 对时）

### 2.1 数据流

```
字节流来源(每个网关一个：串口，或字节转发器提供的 TCP 连接) → 拆帧/CRC → 原始日志(追加写，唯一事实来源)
      → 重组(去重/排序/丢失判定) → 时间模型 → 处理后数据存储 → 事件分类 → 位置推算 → 跨料架复现分析 → 查看/报表
```

所有处理结果应能从原始日志重新生成，算法变更后可以重新处理历史数据。

### 2.2 原始日志

- 每个网关每小时一个文件：`raw/YYYYMMDD/HH_gw{id}.bin`。
- 每条记录：`u64 pc_recv_ns + u16 len + 主机帧原文`。
- 出站 `TIME_REQ` 也按相同记录格式保存，此时首字段为 PC 发送时刻；方向由主机帧 type 区分。没有 t1 就不能从原始日志重算网关到 UTC 的映射。
- 每秒 flush + fsync。模式 A 约 2 GB/天/节点；模式 B 30 个节点合计每天约几百 MB（取决于事件数量）。

### 2.3 网关时间 → UTC

- 每 1 s 向每个网关发 TIME_REQ，记录服务器发送时刻 t1、接收时刻 t4（`time.time_ns()`），配合 t_req_us / t_resp_us 做类 NTP 计算。
- 60 s 窗口内只取 RTT 最小的 20% 样本做线性拟合 `pc_ns = a·gw_us + b`。USB 直连预期误差约 0.5 ms；经小主机转发时多一段局域网延迟，预期 ≤ 1 ms，需实测。转发器只转发字节，不改时间戳。
- 服务器系统时钟用 chrony 对工厂 NTP 服务器。Windows 的 w32time 精度不够，不推荐。
- 网关 TIME_RESP 计数倒退时建立新时钟 epoch，以有序字节流中的 HELLO 确定重启边界；GET_INFO 的普通 HELLO 不单独切段。
  同一次读取中可能同时包含旧帧、HELLO 和新帧，PC 时间戳也可能相同，边界因此按原始记录顺序区分，不改变原始日志格式。
  缺少 HELLO 栅栏且 epoch 归属有歧义时保留 `t_utc_ns=NULL`，不沿用旧时钟模型伪造 UTC。

### 2.4 重组（每个 node_id + boot_id 一个实例）

- 按 02 §7 的规则去重、排序、判定永久丢失，输出：样本块、锚点、同步配对、STATUS、缺口记录（区间 + 原因）。
- u32 字段（seq、sample_idx、各种 _us）一律先展开成 int64 再使用。
- 多个网关收到同一包时合并处理；每份副本的 rx_us 归属到各自网关的时间模型。
- 模式 B 的 SUMMARY / EVENT 包同样按 (node_id, boot_id, seq) 处理，格式见 05。
- 实时重排窗口设计为 5 s；更迟到的帧仍应保留在原始日志中。采集结束后应从原始日志完整重排，恢复全部已收到的有效样本。

### 2.5 时间模型（三级串联）

1. `sample_idx → 节点时间`：每个 segment 用锚点做滑动窗口（30 s）稳健线性拟合，得到实际 ODR，模式 A 残差目标 < 50 µs，模式 B 预期 < 100 µs。当前阶段一模式 A 同样使用分辨率约 30.5 µs 的 RTC，实际残差需接板测量。
2. `节点时间 → 网关时间`：用 `(sync_txdone_us, 对应副本的 rx_us)` 配对拟合，窗口 30 s，剔除 3σ 外的点；节点换网关时换用对应网关的配对。
   盲区期间没有配对，用盲区前后两段拟合结果做线性插值。
3. `网关时间 → UTC`：见 2.3。
- 每个样本 `t_utc_ns = f3(f2(f1(idx)))`。每级每小时记录残差统计，任一级 > 1 ms 时告警。
- 所有网关都对齐服务器时钟，左右节点之间预期 ≤ 2 ms，足够对比 5~10 ms 的事件。

### 2.6 处理后数据存储

- 每节点每小时一个 Parquet 文件（zstd 压缩）：`sample_idx(i64)、t_utc_ns(i64)、ax/ay/az(i16 原始值)、flags(u8)、segment(u16)`，
  文件元数据记 range、odr、node_id、carrier_id、side。
- SQLite：nodes、gateways、gaps、status、summaries、events、positions、time_model_quality 表。
- 模式 B 的每秒统计值写 SQLite（或按天 Parquet），事件波形按事件存 Parquet。
- 保留策略可配置：原始日志 30 天，Parquet 90 天，事件永久。

### 2.7 事件检测与分类（规则法起步，阈值全部放 YAML）

预处理：原始值 → g（±16 g 时 2048 LSB/g）；每轴 4 阶 Butterworth 高通 10 Hz（离线零相位，在线因果）去掉重力和慢变运动。

基线：每轴 1 s 滑动 RMS；基线取 10 分钟滑动中位数；噪声尺度取安静窗口的 MAD。

检出：高通后矢量幅值 > max(k × 基线 RMS, 绝对下限 g)，k 默认 6；20 ms 内的触发合并为一个事件；保存 [−50 ms, +100 ms] 波形窗口。

特征：起止时刻、持续时间、各轴有符号峰值、主导轴、矢量峰值、能量 ∫a²dt、峰值因子、峭度、上升时间、主频（窗口 FFT）、
运行方向速度变化 Δv_x = ∫a_x dt（事件窗口内）。

初始分类规则（现场标注后调整）：

| 类别 | 判据 |
|---|---|
| 正常运行 | 无事件；每分钟记录 RMS/峰值/峭度趋势，用于观察轴承劣化 |
| 冲击 | 持续 ≤ 15 ms，峰值因子 > 5，主频 > 200 Hz，Δv 不明显 |
| 凸跳 | Z（竖直）轴主导，先正后负（或反之）双极性，持续 5~30 ms，整体 Δv_z ≈ 0 |
| 卡顿 | X（运行方向）轴主导，先减速后恢复，Δv_x 明显，主频 < 100 Hz |
| 左右不一致 | 左右节点 ±20 ms 内配对；只出现在一侧 → 该侧局部缺陷；比较两侧 Δv_x 差 |

模式 A 的全量数据和模式 B 上传的事件波形用同一套分类代码；模式 B 节点端只做初筛，分类在服务器上做。

复现分析（30 个节点后最有价值的部分）：
- 多台料架在同一线体位置（±5 m）都出现事件 → 固定位置缺陷（轨道接缝、导轨变形、固定滚轮）。
- 同一台料架在不同位置反复出现 → 随料架移动的缺陷（该料架下的链条滚轮或轴承）。
- 某一侧持续多于另一侧 → 该侧链条问题。
- 统计值（RMS、峭度）按料架、按位置做长期趋势，用于发现逐渐劣化。

### 2.8 料架与位置（无 PLC）

- 料架：节点固定在料架上，配置文件维护 `node_id → 料架号 → 左/右`，更换料架或节点时更新。车身号拿不到 PLC 时不做，后续可从排产表导入。
- 方案 P2（默认，无需改硬件）：网关安装位置已知。节点经过网关时，该网关收到的 RSSI 随时间先升后降，
  用平滑后的峰值时刻作为"过站时刻"。相邻两次过站的距离 ÷ 时间得到线速；
  位置 = 上一个网关位置 + 线速 × (t − t_过站)。用加速度 RMS 判断停线（RMS 接近零时位置冻结）。
  POLL 和 SUMMARY 包都能提供 RSSI，模式 B 每秒至少 1 个点。预期精度数米，取决于网关间距和 RSSI 起伏。
- 方案 P3（需要改硬件，精度厘米级）：在轨道已知位置固定磁铁，节点加低功耗霍尔开关（µA 级）接可唤醒 GPIO，
  经过时记录时间戳并随 SUMMARY 上报；用两个磁铁的间距编码区分原点。
- 位置引擎输出每个节点的 `t_utc → 线体坐标`，事件按时间查到位置。

### 2.9 查看与报表

界面需求：时间轴缩放查看原始波形、事件列表（时间、料架、左/右、线体位置、类别）、缺口标示、导出 CSV；
线体位置热力图（横轴线体坐标，纵轴日期，颜色为事件数）；节点健康页（电池、太阳能、漫游、丢包率）；日报表。
